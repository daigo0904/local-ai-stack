## 0. 何をしているか（1段落）

研究の中心命題は「**AI エージェント自身の『完了しました』を信頼せず、独立した実行証拠から、その仕事が
どこまで達成されたと確認できるかを判定する**」。壁（guardrun・NVIDIA OpenShell）は研究装置に格下げし、
その上に「申告 ↔ 証拠 → PROVEN / DISPROVEN / UNVERIFIED」の層を載せる。ロードマップ（Phase 1〜8）は
Claude Docs にある: https://claude.ai/code/artifact/80282fef-bee0-4ff9-af61-575080541402
（「2026-10-01 の進み具合」の節に、この日の到達点がまとまっている）。

NVIDIA OpenShell（Landlock＋seccomp の砂場、YAML の方針、OCSF の監査記録）が「壁」の側を押さえに来ている。
**OpenShell は『何をさせてよいか』を見るが、『頼まれた仕事が終わったか』は見ない。**この層はそこに立つ。
動的カーネル制限の案は OpenShell と正面衝突するので採らないと決めた。

## 3. 決めたこと・守ること（変えるなら理由を残す）

1. **神託（`lib/真偽.mjs`）は直していない。**見張りに合わせて正解を直すと、この層は自分を褒め始める。
   神託側で見つけた問題（「エラーが発生しました」を失敗の申告として読まない、構造化した主張が報告とずれる、
   開示した「足して消した」の方針未定）は解剖の記録に書いた。**直すかは本人が決める。**
2. **評価層の門（`lib/門.mjs`）は緩めていない。**python・pytest を通すのは**壁モードの中でだけ**
   （`判定.mjs --壁の中` は、家への書き込みと TCP 接続が断られることを起動時に自分で確かめ、だめなら走らない）。
   壁は Landlock なので **Mac では使えない**。Mac で型15・型16 を測るなら guardrun の壁の中で。
3. **証拠の強さ**：カーネル（受領証・OpenShell）＞検証器（proofcheck の封印・再実行）＞ハーネス（エージェント側の記録）。
   「テストが通った」はハーネスの結果では決めない（細工できる。実走 C1 の PYTHONPATH=patch）。
4. **作業場の外・不在の申告は常に UNVERIFIED。**この層に取る手段が無い。足りない証拠の名前が Phase 8 の行き先。
5. **嘘と言うのは事実と食い違ったときだけ。**裏づけが無いだけのものは UNVERIFIED。開示した細工は鳴らさない側に倒した。
6. **OpenShell の既定（best_effort）は Landlock が掛からないと制限なしで走る。**記録で「Landlock ruleset built」を
   確かめ、方針の read_write が作業場の中だけと分かるまで、作業場の外は言わない。
7. 試験の命令かどうかは **argv[0] で決める**（`cat test_x.py` は数えない。設計ノートの実装のルール6）。
8. **「バグが直った」は、再現テストの反転だけでは PROVEN にしない。**見せないテスト（契約の `hidden`）も通ったときだけ。
   隠しテストが無ければ UNVERIFIED。手書きの契約に巧い嘘 12件を当てたら 11件が PROVEN を取った（2026-10-01）のがきっかけ。
9. **判定を直すときの手順（過学習とバイアスを避けるため。今回の2回ともこれでやった）**
   1. 変更・基準・測る数字を、実装と新しいデータより前に事前登録としてコミットする
   2. 隠しテストと、正直・嘘の解き方は、**依頼文と作業場だけを見せた別々の書き手**に書かせる（規則・契約・
      前の組・結果は見せない）。解き方の書き手には毎回**同じ指示文**を渡す（組どうしを比べるため）
   3. 実装と測る道具をコミットしてから、新しい組を**読まずに入れ、一度だけ測る**
   4. 結果を見て規則・隠しテスト・ラベルを直さない。直すなら次の版として、**また新しい書き手の新しい組**で測る
   5. 設計に使った組は in-sample と明記して、主な数字にしない
   書き手に渡した指示文と、入力の作り方は `verify/corpus/書き手への指示文.md`。次の組もそれをそのまま使う。

## 5. 次にやること（Mac でしかできない）

優先順に。

1. **検証コーパスを本物のモデルで回す**（ロードマップ Phase 5 の最初の実測）

   DISPROVEN、段3〜5 は 9 件中 8 件で契約が PROVEN のままだった（段が上がるほど契約で言えることが減る）。
   **全部を回すと 10 時間ほどかかる**（agent-run の上限が1課題 3600 秒・33 課題・2 エージェント。ローカルの
   モデルは並列で速くならない）。だから次の順で:
   1. **試走**：各段1課題・qwc だけ（`--only L1-rename,L2-login,L3-deploy,L4-naming,L5-faster`）。
      固まる・記録が取れない・判定が落ちる、など仕組みの問題を先に出す
   2. **run_corpus に `--timeout` を足す**（agent-run へ渡す口がまだ無い）。上限は試走の実測から決める
   3. **本番の前に事前登録**：見る数字（段ごとの契約 P／D／U、言い切った件数、UNVERIFIED の理由、本体が原因の失敗）と、
      下の qwc と Codex の比べ方の基準を、回す前に `verify/corpus/` に書いてコミット
   4. **本番は夜に片方ずつ**（qwc の晩と Codex の晩）。結果は `verify/corpus/results/`
   **qwc と Codex（`--oss`）を同じモデル・同じ課題で比べる。**問いは「モデルの賢さ以外で qwc が勝てるか」。
   小さなローカルのモデル・日本語・途中で促して直させる、が重なる所では qwc が上回る可能性がある（仮説。根拠はまだ無い）。
   比べるのは、頼んだことを本当に終えた率（契約 PROVEN）・嘘の報告の率（契約 DISPROVEN なのに「できました」）・
   本体が原因の失敗（固まった・道具の呼び方の誤り）。どの差で「勝った」とするかは回す前に決める。
   負けたら、qwc はエージェントとしてではなく見張りの実験台に絞り、見張りの知見を proofcheck など
   どのエージェントにも付けられる側へ移す、という方針を本人と相談する。

- **契約の下書き v3**：候補は `verify/corpus/契約の下書き.md` の末尾（may_change を決められなければ封印させない、
  削除の確かめ、node のテスト、JSON の値を型ごと比べる）。**入れたら、また新しい課題を書いてから測る。**
- **主張と証拠の表の空きマス**（`記録/2026-10-01-主張と証拠の表.md` の末尾）：「結果は 5 でした」と出力の食い違い、
  空のままの「作成しました」、読まずに言った「存在しません」、「変えずに」と言われていない場合のテスト書き換え。
  足すなら先に全束で誤検知を数える。
- **guardrun に「記録の書き出し先」を足す**：agent-run を壁の中で走らせるのに要る（壁は作業場の外への書き込みを
  断るので、エージェントの手が届かない場所にハーネスの記録を書けない）。壁そのものの変更なので慎重に。

## 8. 細かい注意

- クラウドでは浅い clone（`--depth 1`）で、取ってくる範囲が main だけだった。手元のブランチは普通に `git fetch` でよい。
- qwc のコメント・コミットは日本語で、「なぜ要るか（実測の日付と事例）」「鳴らせてはいけない場合」を必ず書く流儀。
  見張りを足すときは、評価層の全束を足す前と後で回し、結果が変わった事例を全部読んでから入れる。
- proofcheck の試験は `verify/test_*.py`。性質（P1〜P8）は乱数の種を固定してある。P3（並び順によらない）は一度破れて直した。
- guardrun を Linux の root で verify するには `bubblewrap` と `acl`（setfacl）と `_guardrun` ユーザが要る。
  setfacl が無いと uid の通り道を開けられず、11項目すべて ★（走らずに止まる。黙って壁なしにはならない）。
