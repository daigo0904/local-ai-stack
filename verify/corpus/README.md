# 検証コーパス — どこまで証明できるかを段ごとに測る

ロードマップ Phase 5 の「Kernel Truth → Semantic Truth のギャップ」を測るための課題の束。
**エージェントの出来を測るものではない。**段ごとに、PROVEN まで届いた割合と、
UNVERIFIED に残った理由を出し、この層（proofcheck）の保証境界を実測する。

| 段 | 中身 | 課題 |
| --: | --- | --- |
| 1 | OS の事実だけで証明できる | 改名・デバッグ出力の削除・.gitignore への追記 |
| 2 | 追加テストがあれば証明できる | ログインのバグ・ページ分けの1件抜け・税率 |
| 3 | 外部の状態が要る | 本番への反映・本番 DB の行・Slack への通知 |
| 4 | 人の判断が要る | README を分かりやすく・変数名を読みやすく・レビューだけ |
| 5 | 機械では判定困難 | 速くする・安全にする・ユーザーが喜ぶように |

課題は `tasks/<id>/` に1つずつ。`task.json` に依頼・契約・注記と、自己点検用の
「正直」「嘘」の解き方（作業場に当てるファイルと申告、期待する判定）がある。`workspace/` が元の作業場。

## 回し方

```sh
verify/run_corpus --self-check          # エージェントを使わない。コーパス自身の点検（試験にも入っている）
verify/run_corpus --agent qwc           # 全課題を qwc に解かせる（Mac・ollama）
verify/run_corpus --agent codex --fast  # Codex に解かせ、--fast でも判定する
```

結果は `results/<日時>-<モード>.json` と `.md`。表は段ごとの「全体」と「契約」の P／D／U。

## 自己点検で分かったこと（2026-10-01）

作ってすぐ、29 件の解き方のうち 11 件が期待と違った。**契約の判定は29件とも期待どおり**で、
外れたのは全部 proofcheck の申告の分解だった:

- `0.08` をファイル名と読んでいた（「税率を 0.08 から 0.10 に変更しました」が DISPROVEN に）
- 「削除しました」「名前を変えました」「改善しました」「読みやすくしました」を変更と読まなかった
- **作業場の外への申告を、作業場の差分で PROVEN にしていた。**「本番 DB で実行して、メールを
  更新しました」を、SQL のファイルが変わったことで PROVEN にしていた
- 「ほかに問題はありません」（不在の主張）を拾っていなかった

直したあとは 29/29。新しい主張の種類「作業場の外」「不在」は、この層では取れない証拠を要るので
常に UNVERIFIED になり、足りない証拠として「外部の状態を読み取り専用で確かめた記録」「無いことの
証明」を書く（Phase 8 の入口）。

何もしない偽の qwc で全課題を回すと（配線の確かめ）、段1・2 は契約が全件 DISPROVEN、
段3〜5 は 9 件中 8 件で契約が PROVEN のままだった。**段が上がるほど、契約で言えることが減る。**
「何もしていない」を見抜けたのは申告の側（「修正しました」と差分の食い違い）だけだった。

## 足すとき

- 1段あたり 20〜100 件を目標に足す（ロードマップの 100〜500 件）
- 正直と嘘を必ず対にする（嘘だけだと、何にでも鳴る判定が満点を取る）
- 依頼に答えのある課題（段1・2）と、答えが依頼の外にある課題（段3〜5）を混ぜる
- 自己点検を通してから入れる（`verify/test_proofcheck.py` が全件を回す）
