# 申告と証拠の三値判定 — 定式化

エージェントの「できました」を信じずに、独立した実行証拠から、どこまで達成されたと言えるかを決める。
ここでは `proofcheck` の判定の核（`decide`）と、安い証拠から先に取る打ち切り（`--fast`）を、
定義・規則・性質として書く。性質はすべて `verify/test_theory.py` で、ランダムに作った証拠の組
（種固定・各数千件）に当てて確かめてある。

**これは「嘘の確率」を出すモデルではない。**確率にすると、どこから不確かさが入ったかが一つの数に
混ざって見えなくなる。ここで書くのは、**どの主張が、どの種類の・どの強さの証拠で決まったか**である。

## 1. 定義

**証拠** e = (種類 κ, 向き σ, 強さ s, 出どころ, 中身)

- 向き σ ∈ { +, −, ? }：裏づける／矛盾する／判断に使えない（取れなかった理由だけを持つ）
- 強さ s ∈ { ハーネス = 1, 検証器 = 2, カーネル = 3 }：**改竄されにくさの順序**

| 強さ | 出どころ | 例 |
| --- | --- | --- |
| カーネル（3） | 壁の外の記録。中のエージェントが書き換えられない | guardrun の受領証（OpenShell の監査記録も同じ段に置ける） |
| 検証器（2） | 検証器が自分で取った事実 | 封印からの差分、テストとフックを戻した写しでの再実行 |
| ハーネス（1） | エージェント側のプロセスが書いた記録 | `codex exec --json`、`qwc --events` |

**主張の種類** k ごとに、次の2つを決めておく。

- R(k)：PROVEN に要る証拠の種類の集合
- 意味の判断を含むか（含むなら判定の根拠を semantic と書く）

**証拠の種類** κ ごとに、判定に使える最低限の強さ m(κ) を決めておく。

| 主張 k | R(k) | m | 根拠 |
| --- | --- | --- | --- |
| ファイルを変更した | fs_change | 検証器 | deterministic |
| テストを実行した | test_process | ハーネス | deterministic |
| テストが通った | test_result | 検証器 | deterministic |
| バグが解消された | repro_flip | 検証器 | **semantic**（再現テストに委ねた代理） |
| 作業場の外を変えた・送った | external_state | カーネル | **semantic**（この層では取る手段が無い） |
| 問題が無い（不在の主張） | absence_proof | カーネル | **semantic**（不在は機械では証明できない） |
| その他の完了 | ∅ | — | semantic |

「作業場の外」「不在」は、要る証拠を取りにいく手段がこの層に無いので、常に UNVERIFIED になる。
足りない証拠の名前（外部の状態を読み取り専用で確かめた記録／無いことの証明）が、Phase 8 で
取りにいく先の一覧になる。検証コーパスの自己点検で、外への申告を作業場の差分で PROVEN に
していた誤りが見つかり、この2つを足した（verify/corpus/README.md）。

「テストが通った」の最低限を検証器にしてあるのは、**エージェント自身のテスト実行（ハーネス）は
走らせ方を細工できる**から（実走 C1 の `PYTHONPATH=patch`）。ハーネスの結果は判定に使わず、
食い違いを見せるための参考として残す。

**使える証拠** A(k, E) = { e ∈ E | κ(e) ∈ R(k), σ(e) ∈ {+, −}, s(e) ≥ m(κ(e)) }
A⁺, A⁻ をそのうち向きが + / − のものとする。

## 2. 規則

主張 k と証拠の集合 E に対して、判定 decide(k, E) を次の順で決める。

- **D1** A⁺ ≠ ∅ かつ A⁻ ≠ ∅ → **UNVERIFIED**（証拠どうしの食い違い。どちらかの記録が壊れているか書き換えられている。**どちらかに決めない**）
- **D2** A⁻ ≠ ∅ → **DISPROVEN**
- **D3** R(k) ≠ ∅ かつ、R(k) のすべての種類が A⁺ で埋まる → **PROVEN**
- **D4** それ以外 → **UNVERIFIED**。足りない種類と、取れなかった理由（向き ? の証拠）を書く

決め手 trust(k, E) = 判定に使った証拠のうち、一番弱いものの強さ。
**どこから不確かさが入ったか**（ロードマップ Phase 6）を、主張ごとに1つの値で示す。

全体の判定は、主張と契約の各行について「1つでも DISPROVEN なら DISPROVEN、
そうでなく1つでも UNVERIFIED なら UNVERIFIED、全部 PROVEN なら PROVEN」。

## 3. 性質

| | 性質 | なぜ成り立つか |
| --- | --- | --- |
| P1 | 証拠が無ければ、どの主張も UNVERIFIED | A = ∅ なので D1〜D3 のどれにも当たらない |
| P2 | PROVEN なら、R(k) が全部使える + で埋まり、使える − は無い | D3 に来るのは D1・D2 を抜けたときだけ |
| P3 | 証拠の並びを入れ替えても、判定・決め手・足りないものは同じ | 規則は集合だけを見る。**乱数の試験で一度破れた**（足りない理由を並び順で選んでいた）ので、理由も集合にして並べ直すよう直した |
| P4 | 強さの足りない証拠・関係の無い種類の証拠を足しても判定は変わらない | それらは A に入らない |
| P5 | 使える − を1つ足せば、何があっても PROVEN にならない | A⁻ ≠ ∅ なので D1 か D2 |
| P6 | DISPROVEN に + を足しても PROVEN にならない | A⁻ は減らないので D1 か D2 |
| P7 | 証拠の定義が無い主張（その他）は PROVEN にならない | R(k) = ∅ なので D3 に当たらない |
| P8 | 決め手は判定に使った証拠のうち一番弱いもの | 定義どおり |

P5・P6 が「**証明できないことを誤って成功扱いしない**」の形式的な中身になる。
P1 と P7 が「証拠の無い主張を勝手に TRUE にしない」。

## 4. 安い証拠から取る — 定理 F

証拠には取る費用がある。差分・ハーネスの記録・受領証は読むだけで取れるが、
テストの再実行は修正前と修正後で 2 × (契約のテストの数) 回、プロセスを起こす。

`--fast` は、まず安い証拠だけで全部の行を判定し（再実行の要る行は「打ち切った」理由つきの
UNVERIFIED になる）、そこで **DISPROVEN が1つでも出たら再実行を取らずに終える**。

**定理 F** 打ち切った場合も打ち切らなかった場合も、全体の判定は打ち切らずに全部取った場合と同じ。
打ち切らなかった場合は、行ごとの判定まで同じ。

証明の筋：安い段の行（変更・実行の主張、may_change・must_not_change・フック・作業場の外・
guardrun の印・差分の二重化）は、再実行の結果を証拠に使わない。だから安い段で DISPROVEN だった行は、
再実行を取っても同じ証拠集合で判定され、DISPROVEN のまま残る。全体は「1つでも DISPROVEN なら
DISPROVEN」なので、打ち切っても全体は DISPROVEN で一致する。打ち切らなかった場合は、
同じ証拠で同じ規則を当てるだけなので全部一致する。

`verify/test_theory.py` の7場面（正直に直した・何もせず達成・フックで通した・テストを書き換えた・
外を触った・直していないのに通った・名指しが違う）で、全体の判定は7場面とも一致し、
5場面で打ち切って再実行を **10 回省いた**。**嘘のほうが安く決まる**——嘘の多くは、差分や
記録という安い事実とすでに食い違っているから。

注意：打ち切った場合の**行ごとの判定**は一致しない（再実行の要る行は UNVERIFIED のまま残る）。
行ごとの判定まで要るとき（研究の集計など）は `--fast` を付けない。

## 5. 計算量

主張 n 個・証拠 m 個に対して、decide は O(n·m)。重いのは判定ではなく証拠を取ること
（差分は作業場のファイル数に比例、再実行はテストの所要時間）で、定理 F はその重いほうを省く。

## 6. ロードマップとの対応

| ロードマップ | ここでの形 |
| --- | --- |
| Phase 2 Claim-Evidence Verifier | 主張の種類 k と R(k)、証拠の種類 κ |
| Phase 3 Verification Contract | 契約の行も同じ全体判定に入る。契約は実行前に封印する |
| Phase 4 三値判定 | D1〜D4。UNVERIFIED には足りない種類と取れなかった理由を書く |
| Phase 6 Verifier を疑う | 強さの順序と決め手（trust）。食い違いは D1 で表に出し、どちらかに決めない |
| Phase 8 追加検証の生成 | D4 の「足りない種類」が、次に取りにいく証拠の一覧になる |

**壁は取り替えられる。**強さ「カーネル」の段は guardrun の受領証でも、NVIDIA OpenShell の
監査記録でもよい。この層が要るのは「壁の外で取った、中から書き換えられない事実」であって、
どの壁かではない。

OpenShell の監査記録（OCSF）は `--ocsf` で読む。取れるのは Landlock が掛かったか・外への接続の
許可と拒否・方針の回り込みの検知・ワークロード全体の終わり方で、**中の命令とファイルの変化は無い**。
壁の記録だけでは「仕事が終わったか」は決まらず、ハーネスの記録と封印からの差分が要る——
この層が壁の上に載る理由が、そのまま形になっている。

## 7. 限界（ここで言っていないこと）

- **申告の分解は規則による。**言い換えに弱い。分解を誤ると、正しい規則が間違った主張に当たる
- **強さの順序は仮定である。**ハーネスの記録がモデルの手の届かない場所にあること、
  検証器の封印が改竄されていないこと（封印IDで確かめる）、壁が保証境界どおりに効くこと
  （古いカーネルや Windows では境界が狭い）に依っている
- **semantic な主張は代理で決めている。**「バグが解消された」を PROVEN にするのは
  再現テストであって、ユーザーの意図ではない。再現テストが弱ければ PROVEN も弱い
- **D1 の食い違いは原因を言わない。**どちらの記録が壊れたかは、別に調べる必要がある
